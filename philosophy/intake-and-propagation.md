# 投资思想的持续收纳与全体系同步机制（v0.1）

> 核心用途：项目所有者可**不定期、自由地在对话中**提出投资想法；当对话明确指向本项目，研究助手应当把相关想法归档、梳理并将已经确定的操作要求同步到依赖文件及定时任务。不是要求所有者填写表单或每次先提出正式变更申请。

## 1. 每次讨论的处理顺序

1. **原意提炼**：识别新想法、对原观点的修正、例子、疑问、反例与具体执行要求；不把比喻、举例百分比或试探性问题误当成可普遍适用的定律。尽可能保留所有者原意，少量必要解释与助手扩展分别标注。
2. **归类与状态**：将条目标为 `想法/待澄清`、`研究假设/待证据`、`已明确的研究偏好` 或 `已确认的执行要求`。只在内容清楚时归类，无需每次打断讨论问形式化问题；若改变研究结果或重要行为且意图不清，注明待确认而不要擅自定稿。对本库编辑者提炼稿加 `待所有者逐字审核`，即使可据清晰执行要求开展工作，也不伪称逐字确认。
3. **标识与关联**：给长期原则 `Pxx`，给新增想法 `IDEA-YYYYMMDD-序号`，记录提出日期、议题、简短意旨、状态、影响范围、与既有 Pxx 的支持/补充/冲突关系，以及对应 GitHub commit/文件；不保存对话全文、私密信息或个人财务资料。必要时写入 [`ideas.md`](ideas.md)。
4. **变更影响分析**：检查思想核心、研究宪章、`metadata/` 方法、报告格式、数据/验证、网站摘要提取、监控测试、日报/周报/月报自动任务、README/公开说明中哪些需要同步。依 [`integration-map.md`](integration-map.md) 逐项记录 `已更新/无需改动/待处理+原因`。
5. **实施与检查**：先更新规范、再更新依赖执行说明与任务（保留原定时和用户认可的公开/免费模式），如牵涉网站生成器则测试和部署；检查链接、格式与证据边界。每次 GitHub 写入前核实 canonical public repo 及 push 权限，绝不为了同步而改写不可变历史报告或倒填行情。
6. **记录结果**：更新 [`change-log.md`](change-log.md)，说明日期、思想条目、修改的路径与任务、验证结果、未完事项；对所有者如实报告已做/未做，不能声称未执行的验证已经通过。

## 2. 冲突与迭代规则

- 新想法如果与旧思想**措辞冲突**，先辨别是否只是适用期限、情景或定义不同；不能静默删除旧思想。
- 若新思想确实替代旧思想，在 `ideas.md` 写 `修订/取代 Pxx` 的关联，并在 `change-log.md` 留下理由和生效版本。正式历史报告不回写；之后的新报告引用新版本。
- 若思想与可靠事实冲突，事实优先；记录思想可能需要调整而不是把反证过滤掉。无证据支持的经济理论保留为待检验观点。
- 修订不得抹除失败的投资假设、只保留成功案例，也不能将研究偏好升级成股票的必涨/必跌事实。

## 3. 实际执行的边界

本机制让仓库成为**跨对话可检索的持久权威记录**，而不是声称聊天本身能永久自动记住所有内容。仅当相关对话及仓库连接可用时，助手才能把内容直接写入 GitHub；若连接或权限不足，须说明实际未入库，给出可保存的草案。不会在用户未发起对话时自行监听其想法；只有用户另行要求并创建的定时任务才按既定频率运行。一次讨论影响的所有文件也不能在验证失败时假称完成。

## 4. 每次修改的最小交付清单

- [ ] 忠实摘要、来源日期、状态与是否属于所有者本人的明确观点
- [ ] 新思想与旧原则的关系及冲突说明
- [ ] `core-beliefs.md`／`ideas.md` 与宪章的必要更新
- [ ] `metadata/` 方法和研究模板的影响检查
- [ ] 日报/周报/月报及网站/工具/测试的影响检查
- [ ] 实际 GitHub 写入与权限核对、必要时 CI/站外检查
- [ ] `change-log.md` 记录、链接及明确未完成项

“不适用/无须修改”也应有简单理由，避免以“已全面更新”掩盖遗漏。
